# Vietnam needs re-running on a machine that has `../thesis`

The US and Japan halves of this branch were re-run and their results are
current. **Vietnam's are not.** Its notebooks and results are the ones already
on `main` — restored unchanged, not regenerated — because the Vietnamese data
pipeline cannot run in this checkout.

## Why it could not run here

`scripts/build_vietnam_data.py` reads the sibling preprocessing repository
`../thesis`, which is not present. Without it three caches are missing:

| File | Present |
|---|---|
| `data/vietnam_prices.csv.gz` | yes |
| `data/vietnam_scores.csv` | yes |
| `data/vietnam_fundamentals.csv` | **no** |
| `data/vietnam_sectors.csv` | **no** |
| `data/vietnam_benchmarks.csv.gz` | **no** |
| `data/vietnam_score_exclusions.csv` | **no** |

Two things fail as a result, for two different reasons:

* **`notebooks/05_vietnam_full_study.ipynb`** calls `load_cached("vietnam")`,
  which needs all four canonical caches. It fails on its first cell.
* **`notebooks/grid/vietnam_grid.ipynb`** gets further than expected:
  `load_scores` succeeds, because `vietnam_scores.csv` is shipped. What fails
  is `exclusion_report`, which finds no `vietnam_score_exclusions.csv` and
  falls back to recomputing from an FS_clean workbook that Vietnam does not
  have. The generator now degrades gracefully here — it reports the scored
  counts it can see and leaves the unavailable gates at zero rather than
  inventing them — so on a machine that *does* have the ledger, nothing
  changes, and on one that does not, the notebook runs with a stated gap.

## What to do

On a machine with `../thesis`:

```bash
python scripts/build_vietnam_data.py
```

```bash
python scripts/build_grid_notebooks.py execute vietnam
```

```bash
python scripts/build_notebooks.py
```

then execute `notebooks/05_vietnam_full_study.ipynb`.

## What changed under Vietnam's feet, and why a re-run is not optional

The Vietnamese notebooks restored here were generated by `main`'s version of
the generators. The generators on this branch have since changed for reasons
that apply to all three markets, so **regenerating Vietnam will produce a
different notebook from the one committed**:

* **Per-market loaders.** The US and Japan now score from canonical statements
  through `fscore.data.score_panel`, so each market's grid reads the same
  statements its main study reads. Vietnam keeps `load_scores` — its sibling
  pipeline already ships a scored panel — but the loader is now selected from
  a dict rather than hard-coded, and Vietnam's entry carries the fallback
  described above.
* **One exclusion table and figure for three markets.** Markets count
  different things: the developed pair record which EQ_OFFER measure each
  firm-year used, Vietnam records gates the others have no analogue for
  (tradability, accounting checks). Missing columns are filled with zero, so
  one figure serves all three; the EQ_OFFER panel is drawn only where that
  split exists, which means Vietnam's exclusion figure keeps a single panel.
* **Corrected source notes.** `main`'s `SOURCE_NOTE` for the US and Japan
  still described the FS_clean workbook, which stopped being true when those
  markets moved to SEC EDGAR and the Bloomberg tree. Vietnam's note is
  unchanged.

None of this changes any Vietnamese *number* — the score panel, prices and
grid mechanics are untouched. What changes is the notebook's prose, its
exclusion table, and the shape of one figure. Re-running is what makes the
committed artefact match the generator that produced it.

## Do not simply regenerate without re-running

`python scripts/build_grid_notebooks.py` (no `execute`) rewrites the notebook
and **strips its outputs**. If Vietnam is regenerated on a machine that cannot
execute it, the committed notebook becomes an empty shell and the record of
the run is lost. Regenerate and execute together, or leave it alone.
